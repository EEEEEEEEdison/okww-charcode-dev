# 知识维护规则

本流程只用于维护者明确要求的仓库知识维护任务。
入口为 [知识维护 Skill](okww-knowledge-maintenance/SKILL.md)。
普通开发流程的知识使用边界见 [语义卡说明](../knowledge/cards/README.md)。

## 1 范围与来源

审核范围由本次维护任务确定。
可检查代码基线、用户回答、实测反馈和与旧条目冲突的新证据。
不得在普通开发或实测结束时自动进入本流程。
来源按 [evidence.md §2](../harness/evidence.md) 获取。
每条证据必须定位到原文、视频时刻或代码版本。

一个角色的一个共鸣链对应一张卡。
文件名为 `<类名>_C<共鸣链>.md`。
不得将一个共鸣链下的观察直接用于其他共鸣链。

## 2 入卡与分流

候选条目必须同时满足：

- 更换作战轴后仍成立；
- 能帮助判断按法、出招顺序或代码实现。

纯养成信息不新增到卡片。
按适用范围选择位置：

| 适用范围 | 写入位置 |
|---|---|
| 单个角色与共鸣链 | `knowledge/cards/<类名>_C<共鸣链>.md` |
| 所有角色通用的写法 | [rules.md](../rules.md) 对应分组 |
| 与角色无关的游戏常识 | [basics.md](../knowledge/basics.md) |
| 只适用当前轴或仍需验证 | 用户工作区的本案 `notes.md` |

## 3 起草与确认

先读同一主题的旧条目，合并重复内容。
被证据推翻的条目直接修正或删除，不保留失效结论。
技能使用描述性名称，如“强化普攻”，不得使用案例轴记号。
“代码经验”只收录修改后经实测确认有效的写法。
用户认可操作意图不能替代机制与数值验证。

用宿主的结构化提问工具集中确认候选：

- 多选题的每个选项对应一条候选。
- label 写“<角色> <节名>：<要点>”。
- description 写完整条目、来源和适用条件。
- 每题最多 4 条，每次调用最多 4 题。
- 只有一条候选时，用“写入”和“不写入”的单选题。

只有用户选择的条目才能写入，并记录确认日期。
分流到 rules.md 和 basics.md 的条目使用相同确认方式。

## 4 卡片模板

```markdown
# <中文名>（<类名>）<共鸣链> 链

## 技能与按法
- <描述性技能名称>：<按法及效果>（来源：<文件与行号、视频时刻或代码版本>；用户确认 <日期>）

## 状态与识别
- <图标或 HUD 变化，识别判据及适用条件>

## 时序
- <起止事件、间隔或时长、计时口径、精度和来源>

## 代码经验
- <已实测的判据、区域、阈值、等待与时限>（来源：<版本目录、函数及实测证据>）

## 补充说明（可选）
- <有助于理解出招意图的机制>
```

每条必须写来源和用户确认日期。
实测数值与写法还必须记录：

- 实测状态：多次一致时写次数，只有一次时写“单次观察”；
- 适用条件：游戏版本、ok-ww 基线和录屏分辨率；
- 时间条目的起止事件、计时口径和测量精度。

时间记录遵守 [timing.md](../harness/timing.md)。
没有实测依据的改法不得写成已验证经验。
只整理本次修改涉及的卡片，不批量重排其他卡片。

## 5 检查

检查改动与已确认候选一致，来源能定位。
检查 Markdown 链接和受影响的引用。
确认普通开发入口仍只读取知识，不触发维护流程。
版本安装规则见 [README](../README.md#使用与安装)。
知识更新随新版本交付，不改写已发布版本的标签。
