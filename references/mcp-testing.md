# MCP 实测操作指引

本指引用于生成代码后的实测，也用于直接测试已有代码。
Agent 负责从程序未启动推进到测试结束，不默认用户摆好界面或选好队伍。
连接配置教程不在本指引范围内。

## 1 先确定待测目标

从用户请求、已有代码和工作区记录中确定：

- 待测源码、工坊覆盖或配队包，以及期望的战斗行为；
- 模式、关卡、目标队伍、槽位顺序和开场角色；
- 测试局数、总时间预算、成败判据及停止条件；
- 启动程序、游戏操作、进入挑战及记录变动的已有授权。

信息已明确时，不必逐项向用户提问。
单个技能、切人分支或循环也可作为测试目标，不必做整队性能评估。
只收到“测试当前队伍”时，先识别当前队伍，不得另选成绩更好的配队。
目标队伍有多个且会影响测试时，必须确认业务选择，不得自行替换。

启动、重启、覆盖代码和消耗游戏资源沿用宿主及工作区的授权规则。
授权已覆盖的操作直接执行；未覆盖的副作用必须在发生前说明并确认。
不得把评估脚本的默认局数当作授权预算。

## 2 从未启动到游戏可操作

### 2.1 检查并启动 ok-ww

1. 读取 `okww-harness.local.md`，定位 `working`、解释器和现有启动入口。
2. 检查该安装目录的进程、工作目录和 MCP 实例记录，复用已有实例。
3. 没有运行实例且已获启动授权时，由 Agent 执行现有入口。
4. 等待进程存活、MCP 服务就绪及工具调用成功，分别记录结果。

不得靠重复启动探测状态。框架单实例机制能替换旧进程。
包装器及其子进程不表示同时运行两个 ok-ww 实例。

安装版宜先核对 `<应用目录>/.pyappify-shortcut.py` 和 `app.json`。
包装入口使用安装版解释器，工作目录为 `working`。
原生 `ok-ww.exe` 可打开启动器；不得臆造“启动应用”的命令行参数。
宿主能操作启动器时，可由 Agent 点击实际识别到的启动控件。

当前框架另有以下入口，使用前必须核对本机 `ok/cli.py`：

| 用途 | 程序与参数 | 工作目录 |
|---|---|---|
| 无 GUI 的 MCP 运行时 | 安装版 Python，`-m ok mcp --config config:config` | `working` |
| GUI 与 MCP | 安装版 Python，`-m ok gui --config config:config --mcp` | `working` |

宜优先复用已验证的项目入口，不得为开 MCP 替换用户正在使用的 GUI。
新进程必须由宿主保持运行；命令提交成功不证明进程持续存活。
直接运行 Python 不会自动获得启动器所需的管理员权限。
遇到系统提权或登录验证时，说明所需用户操作，不得绕过系统保护。

连接记录通常位于 `working/logs/mcp/connections/`。
可用 `ok.core.mcp_server.discover_mcp_servers()` 核对活动实例。
该方法返回的令牌不得写入报告。
端口及进程必须按本次实例核对，不得把兼容快照或固定端口当作存活证据。
宿主工具未恢复时，宜先恢复已配置的连接。
宿主无重连能力且项目已装官方 MCP SDK 时，可用薄客户端访问同一实例。
客户端仍必须调用 `list_skills` 和 `get_skill`，令牌只用于鉴权。
不得另起服务器或修改宿主连接配置来替代重连。
两种调用方式均不可用时，记录连接缺口及仍能完成的静态检查。

薄客户端必须使用本机 SDK 的字段名，不得从协议 JSON 推断对象属性。
历史 `mcp==2.3.0` 使用 `server_info`、`protocol_version` 等 snake_case 属性。
同版还使用 `input_schema`、`is_error` 和 `structured_content`。
`serverInfo` 曾触发 `AttributeError`；更换 SDK 版本后必须重新核对。
Windows Python 使用 `-I` 时会忽略 `PYTHONIOENCODING`。
客户端需输出中文时，先用 `sys.stdout.reconfigure(encoding='utf-8')`。
输出重定向到文件时，也必须明确使用 UTF-8。

### 2.2 通过 ok-ww 启动游戏

MCP 可用后，先按 [MCP Skill](../skills/mcp/SKILL.md) 发现并读取内置指引。
再提交仅做启动与界面取证的薄 Task，不得直接提交评估脚本。

当前 runner 在执行 Task 前准备设备。
配置允许启动游戏时，准备阶段调用 `StartController.start_device()`。
框架复用现有游戏路径、启动参数及窗口等待，不必另写游戏启动器。
路径或权限缺失时，必须报告原始失败，不得猜测账号或安装路径。

启动后必须分别确认：

- 游戏进程及窗口出现；
- 取得正确窗口的新鲜画面；
- 游戏已进入能继续导航的界面；
- 输入操作产生了预期的可见变化。

游戏窗口出现不证明已登录。MCP 执行期间，触发任务不会自动接手。
登录、公告或月卡页宜复用当前项目的自动登录方法。
用 `list_tasks()` 核对 `AutoLoginTask`，再取得其注册实例。
`login.wait_login()` 每次只推进当前状态，需刷新帧并有界重复。
`login.handle_monthly_card()` 可处理已识别的月卡页。
`logged_in` 是缓存；旧标志与本帧不符时，先核对再修正。
登录完成必须用新鲜画面确认，不能依赖 `login.run()` 返回值。

调用前必须识别登录页面及本次会触发的分支。
当前 `wait_login()` 能接受隐私条款，也能确认更新后重启游戏。
遇到这些页面且授权未覆盖时，不得继续调用，必须先取得对应授权。
账号密码、验证码或重新认证不能由通用点击猜测完成。

冷启动宜用 `run_task`，再用 `get_run_status` 等待终态。
`screenshot()` 有短等待上限，不宜用来承担完整冷启动。
启动超时按当前配置及实际状态设置，不得无限等候或反复拉起进程。

## 3 自动到达测试场景

### 3.1 通用推进方法

先读取所选内置技能的起点要求，再判断当前页面。
Agent 必须承担导航和选队，不得默认要求用户先操作到起点。

1. 用新鲜截图识别模式、页面标题、当前关卡及阻挡弹窗。
2. 查当前源码或任务列表，优先复用已有导航方法。
3. 缺少完整导航时，在工作区编写截图驱动的薄 Task。
4. 从已确认页面打开地图或活动入口，识别具名目标后进入或传送。
5. 核对到达的模式及关卡，再按下节选择队伍。
6. 每次状态转换后重新取帧，确认下一页面再操作。

每一步必须有当前状态、目标控件、成功信号、超时和操作上限。
状态无变化时先检查画面、输入后端和遮挡，不得持续盲点。
已有证据不足时先补观察；仍不能识别目标时保存现场并报告阻断。
不得用无界 ESC 循环、固定旧坐标或任意 F 交互补足未知路径。

`wait_in_team_and_world()` 只能辅助确认队伍 HUD，不证明地点正确。
`FastTravelTask` 处理已出现的传送按钮，不负责寻找矩阵或深塔入口。
`openF2Book()`、`zoom_map()` 等片段也不能代替完整导航。

### 3.2 进入前自动选择队伍

目标队伍明确时，由 Agent 操作编队界面。
只评估当前队伍时，保留已确认的角色、配装和槽位。

1. 记录目标的 3 名角色、槽位及当前选择。
2. 识别当前模式的编队入口、槽位和角色列表。
3. 复用当前项目的选队方法；没有方法时，用薄 Task 逐槽选择。
4. 按本帧可见的姓名或头像匹配角色。列表外角色先滚动再重新识别。
5. 读回 3 个槽位，核对角色、顺序及确认按钮。
6. 确认选择后保留截图，进入场内再按 §4 复核。

不能只凭点击成功或队伍名称判定选队正确。
角色被锁定、不可用、受疲劳限制或与目标配装不符时，不得换人凑队。
重新编队、换队或重开会改变记录时，必须先核对实际提示及授权。
选队方法在本机验证前，不得声明完整自动选队已通过。

### 3.3 矩阵与深塔的适用起点

| 场景 | 可复用片段 | 调用前必须确认 |
|---|---|---|
| 终焉矩阵编队详情页 | 识别“前往”后进入，等加载，再找挑战交互 | 模式、轮次、关卡、队伍及资源影响 |
| 矩阵场内 | `walk_until_f(..., target_text=...)` 后交互 | 挑战文字与路标正确，非拾取或其他交互 |
| 深塔当前场内、暂停页、结算页或已选楼层 | `restart_combat_in_abyss()` | 当前关卡、队伍及其全部重开确认操作已获授权 |
| 大世界、地图或活动页 | 当前源码导航片段与截图驱动的薄 Task | 当前入口的可见路径，不得直接调用场内恢复函数 |

`restart_combat_in_abyss()` 会处理重开、确认成绩及通用确认按钮。
它会按 F 开战，调用前必须完成 §4 的非战斗队伍及代码预检。
暂停页或结算页隐藏 HUD 时，先用不触发挑战的路径恢复可见队伍界面。
入场与按 F 捆绑在同一函数时，薄 Task 必须只推进到路标前再预检。
无法完成预检时必须记录阻断，不得调用该函数只为查看队伍。
只在已核对的受支持页面使用；未知弹窗语义不能交给通用确认处理。
调用后还要核对挑战状态，不能以返回 `True` 证明开战成功。

上游 `evaluate-team` 要求从当前场内、暂停页或结算页运行。
它的 `reset_to_start()` 首次执行就会开战，不是只做环境检查。
矩阵与深塔能否共用恢复流程，必须核对当前路标及页面，不能只看计时器。

矩阵历史案例仅验证过“编队详情页→大厅→交互开战→结算”。
该案例没有大世界入口和自动选队证据。
其重开提示会重置当前及后续队伍记录，“前往”旁显示“⚡1”。
实际资源含义以当前界面为准，不能直接推断扣除规则。

## 4 队伍、代码与开场核对

待测代码尚未应用时，先按当前内置指引确定实际加载位置。
内置角色与工坊覆盖必须区分，不能只修改未被加载的副本。
应用前检查代码及目标文件，备份将覆盖的原字节。
发现用户或并行改动时，不得覆盖；应用操作沿用 §1 的授权边界。
只测试时，仅应用用户指定版本，不得夹带战斗逻辑修改。

输入为工坊 zip 时，在已获导入授权的应用侧 Task 中执行：

1. 用 `src.char.CustomCharLoader.inspect_team_archive(zip_path)` 校验归档。
2. 从校验结果取得队伍，用 `get_custom_team_folder(info['team'])` 定位目标。
3. 将旧队伍目录备份到 `self.artifact_directory`，记录原文件校验值。
4. 检查同名 `.backup` 目录；已存在时停止导入，不得覆盖或删除。
5. 写入前重查目标。发现并行改动时停止，不覆盖新内容。
6. 调用 `import_custom_team(info)`，读回 `team.json` 版本和 `code_mode`。
7. 逐个核对角色 `.py`、`.import.py` 与 `info['codes']` 的源码文本。

以上方法均来自 `src.char.CustomCharLoader`，使用前必须核对当前签名。
导入会整目录替换，内部备份在成功后删除，不能用作回滚证据。
文件校验值用于记录原字节；源码比较按加载器的换行规范化规则处理。
导入读回通过不证明内存已更新，仍需完成下节的加载核对。
不得因 shell 文件访问被拒绝，改用 Task 绕过同一权限限制。

### 4.1 核对实际加载的队伍

设备和角色实例操作必须在 MCP Task 的执行器中完成，不得并发调用。
在已确认的非战斗状态、队伍 HUD 可见时，取得注册的 `AutoCombatTask`。
调用 `load_chars()` 后记录：

- 3 个槽位、角色名称、当前槽位及识别置信度；
- 具体类、模块、源码路径和待测源码的校验值；
- 工坊覆盖、有效角色定位，以及会影响测试的配置。

必须与目标队伍及待测版本逐项比较。
`load_chars()` 返回成功不证明角色正确；名称相同也不证明代码已生效。
`in_team()` 从槽位 HUD 推断当前角色，需结合本帧及角色证据复核。
动态类路径可从定义方法的 `__code__.co_filename` 回查。

队伍识别错或角色未知时，按以下顺序处理：

1. 保存全屏和槽位区域，区分 HUD 遮挡、加载过渡和真实选队错误。
2. 过渡中有界等待；已识别的非战斗遮挡可关闭后重新取帧。
3. HUD 稳定但仍存疑时，在非战斗状态清空 `chars` 后冷识别一次。
4. 当前三人队伍可用 `combat.chars = [None, None, None]` 后调用 `load_chars()`。
5. 重新核对姓名、槽位、源码和角色配置，仍不符则停止开战。

识别器匹配失败能退回旧对象，重复 `load_chars()` 不保证重新识别。
不得降低识别阈值或强行绑定预期类来伪造识别通过。
真实选队错误时，返回已识别的编队页面修正；不得修改识别结果凑目标。
需新增模板时，读取当前内置模板指引，留到新帧复核后再测试。

代码未生效与角色认错必须分开处理。
角色代码缓存可按内置清理指引刷新，再在两场之间重新加载。
`reload_tasks()` 只刷新所选注册任务，不保证刷新角色及共享依赖。
工坊加载失败能退回内置类，必须检查加载日志和实际源码。
刷新涉及运行时重启时，必须先保存证据并按已有授权处理。
不得用通用 `importlib.reload()` 掩盖未清理的旧引用。

### 4.2 开战交互、切人与锁敌

1. 识别挑战路标和对应交互文字，再有界接近目标。
2. 交互前保存当前角色、目标开场者及队伍槽位。
3. 发出挑战交互后取新帧，确认任务变化、敌人或挑战计时器。
4. 按已确认的开场要求判断是否切人，再核对实际到场槽位。
5. 需要锁敌时复用当前方法，并用可见目标标记复核。

没有指定开场者时，沿用当前配置，不得默认每场强制切人。
指定开场者已在场时，不必重复切换。
需切换时使用已核实的槽位及当前交互方式，不得套用固定角色编号。
F 前切还是 F 后切，以该场景可接受输入的画面证据为准。

`AutoCombatTask.run_auto_combat()` 及当前评估脚本会调用 `switch_healer()`。
它按“战斗前后切治疗”配置选人，能改变手动设置的开场者。
测试要求指定首位时，必须核对该冲突及实际首个执行者。
只有获准改变开场策略时，才能临时调整，并在结束后恢复。

`wait_combat(target=True, ...)` 会尝试中键，不是锁敌成功的独立判据。
深塔恢复按 F 后强制判战 5 秒，也不是可见开战证据。
倒计时宜用新帧和 `get_abyss_remaining_time(force=True)` 核对。

历史矩阵案例曾在 F 后隔 0.15 秒切坎特蕾拉。
这是特定队伍的一次试验参数，不得用作通用延时或默认开场者。
切人失败或正在战斗时发现队伍错误，保留现场并将该次记为失败。
不得在战斗中清空角色缓存，也不得静默重开掩盖错误。

## 5 使用内置技能或薄 Task 执行

内置技能能满足目标时，按返回的正文和脚本执行。
例如当前队伍评估可使用 `evaluate-team`，候选比较可读取 `improve-team`。
必须核对实际起点、指标、局数和临时设置，不能原样接受所有默认值。
含开战操作的 `reset_to_start()` 只能在 §4 预检通过后提交。
不得等评估器的 `verify_start_state()` 才首次核对目标队伍及代码。

只测试一个行为时，可写最小薄 Task：

- 同步定义 `class Task(BaseTask)`；
- `reset_to_start()` 复用经核对的恢复方法，恢复被中断的导航或挑战；
- `verify_start_state()` 断言场景、队伍、源码及开场条件；
- `run()` 调用实际待测代码，并断言目标行为；
- 在 `finally` 或 `on_destroy()` 释放本轮输入及诊断状态。

测试文件放在队伍工作区的媒体目录或 scratchpad，使用绝对路径提交。
通过 `self.get_task_by_class(...)` 复用已注册实例，ID 和源码从 `list_tasks()` 核对。
行为改动仍放原角色或任务中，薄 Task 不得复制整套战斗逻辑。
只为观察的 Task 可无状态恢复；会改变游戏状态时不得用空恢复假装可重试。

MCP 提交任务后会准备设备，不必额外点击 GUI“开始”或按 F9。
GUI 出现黄色 `Remote Control` 横幅表示执行器被占用，不是报错。
横幅的 `Disconnect` 会请求取消当前执行；点击后仍需等待任务终态。

MCP 运行期间触发任务暂停。
薄 Task 必须显式调用待测代码，不能等自动战斗触发器接手。
`AutoCombatTask.run()` 的返回值只说明其执行分支，不能独立证明战斗通过。
重载成功后才能测试；重载失败仍能保留旧实例，必须先处理失败。

## 6 结果利用与收尾

用 `get_run_status(run_id)` 等待 `succeeded`、`failed` 或 `cancelled`。
`stopping` 仍占执行器；清理完成前不得提交下一次任务。
截图必须检查 `cached` 和 `captured_at`，旧缓存不能证明本次操作生效。
