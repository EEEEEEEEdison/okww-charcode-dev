# 实测迭代

实测同时检查动作效果、触发、切人和耗时。
只提供日志时，可以定位程序行为，不能完成视频时间验收。
证据规则见 [evidence.md](evidence.md)，时间比较见 [timing.md](timing.md)。

## 1 输入与版本核对

- 实际运行的代码版本、zip 路径或校验值；
- ok-ww 框架版本、角色共鸣链、初始资源及场景；
- 对应运行的 `logs/ok-script.log`，通常只有 info 及以上；
- 实测录屏、该版 timeline、参考视频及待测项。

缺少录屏时，先分析日志并标出验证限制。
日志与录屏必须能确认属于同次运行。
版本不明且会影响结论时，先补证，不得混用结果。

## 2 日志与模型核对

按节点检查 `enter` → `exit`，核对是否跳节点或交还框架。
统计 `cast X: ok|fail`、`fallback` 和 `interrupt`。
对照模型检查技能触发、完成和依赖是否达成。
按 `switch_next_char` 的 `has_intro`、`current_con` 核对切人。
日志缺失或字段含义不明时，回到源码核对判据。
画面卡住时，卡点前最后一行 `wait` 指出卡在哪个等待。probe 行按 logging.md L-11 处理。

`enter`、发送按键和确认换人可能是不同事件。
日志 `ok` 不能独立证明目标动作完整结束。
根因方法见 [rules.md](../rules.md) 5-8。

## 3 视频与耗时比较

按 [step1.md §4](step1.md) 查看完整画面和关键区域。
按 timing.md 使用相同事件与口径测量。
不得统一把双方第一次切人当作任何区间的零点。
启动轴和循环轴分别选择同一语义起点。
有剪辑、加速或冻结差异时，先记录可比范围。

输出：

1. 动作差异表：节点 / 预期 / 实际 / 证据 / 影响。
2. 时间差异表：按 timing.md §4，含本段和累计差值。
3. 切人核对表：出场节点 / 预期类型 / 实际类型 / 协奏证据 / 下个节点。
4. 待测项结果：缺项编号 / 验证结果 / 新证据 / 后续处理。

每轮实测后，必须按 [evidence.md §4](evidence.md) 回写缺项记录。
有整队时序时，更新当前版本的 `timeline.json.issues`。
局部任务没有整队时序时，更新 `notes.md` 中的唯一记录。
差异表与阶段记录只引用缺项编号及证据，不再维护另一份状态。

先比较整轮，再定位角色节点和关键动作段。
出现超出参考范围的偏差时，检查边界和干扰后分析内部事件。
不能解释的偏差保留为缺项，不得以无 fallback 判为通过。

### 已验证的取证技巧

以下是具体案例的方法与观察值，不能直接作为所有角色的常量。

- **日志对应视频**：弗坎嘉 v10、v11 用 R 后 HUD 恢复首帧对应 `cast R: ok`，两次误差 ≤0.005 秒。E 冷却首帧比 `cast E: ok` 早 0.16–0.34 秒，只能粗定位。必须先核对当前函数返回语义，并用第二个事件复核偏移。时间换算用脚本，不心算。
- **游戏时间**：同一计时器的差值表示游戏耗时。用技能 CD 替代时，先确认冷却首帧读数及中途是否刷新。弗洛洛案例的首帧为 11.4，不能直接用于其他技能。
- **换人时刻**：生命上限数字能辅助确认角色。弗坎嘉 25 秒轴嘉 s3→坎 s3，按 HUD 样式误定为 107.70 秒，生命上限在 107.10 秒已变化，用户于 2026-10-15 确认。数字相同或遮挡时，必须另用角色与图标复核。
- **冻结排查**：真实与游戏耗时的差值超出采样误差时，细看计时器停走。弗坎嘉案例中的击破停走为 1.3–1.5 秒，之后出现大额白字，见 basics.md H-5。不得单凭停走时长认定击破。
- **整体表现**：同一挑战、同样条件下的结算分数可辅助比较。弗坎嘉 v10 为 5978 分，v11 首版为 5419 分。分数不能替代动作与耗时检查。

## 4 根因、修改与复验

先区分观测、解释和待验证假设，再说明根因与改法。
已有明确修复授权时，执行授权范围内的改动。
关键意图仍不明确时，使用结构化提问工具确认。
根因不明时，不加兜底。
每个试验围绕一个可验证假设，隔离因果影响。

按根因选择阶段：

| 根因 | 返回阶段 |
|---|---|
| 作者意图、按法、依赖或切人解释错误 | [轴解析](../skills/rotation/SKILL.md) |
| 事件边界、口径、参考测量或模型错误 | [时序建模](../skills/timeline/SKILL.md) |
| 函数语义、判据或等待实现错误 | [代码实现](../skills/implementation/SKILL.md) |
| 来源缺失、片段不可读 | [素材获取](../skills/materials/SKILL.md) |

修改写入 `harness-v<N+1>`，不得覆盖旧版。
沿用的 timeline、baseline 和待测项也必须能从新版定位。
改变动作理解或时序时，更新模型并重查受影响的 G2 项。
然后执行 [step2.md §6–8](step2.md) 的定向检查与打包。

新版本 `notes.md` 必须记录：

- 输入版本、录屏、日志和运行条件；
- 差异表、证据路径及计时口径；
- 根因、替代解释和仍未验证的假设；
- 修改位置、预期效果和复验办法；
- 参考测量修正及依据，或沿用的参考记录；
- 待测项记录位置及编号、检查结果和下一阶段。

截图和分析文件放在媒体目录，notes 写相对路径。
README 的出处引用原视频、文字轴和 timeline。

## 5 案例证据

把用户反馈、实测判据和已验证的代码改法记录在本案。
来源必须定位到版本、函数、日志或录屏时刻。
尚未实测的改法标明验证状态。
知识使用边界见 [语义卡说明](../knowledge/cards/README.md#使用边界)。

## 6 完成标准

默认沿用用户为弗坎嘉确定的连续 2 场标准。
其他队伍可按已有明确约定调整。
同一版代码的两场实测必须同时满足：

- 日志没有 `fallback`，节点链和动作判据符合模型；
- 触发方式、协奏切人和依赖符合已确认意图；
- 整轮、节点和关键动作段已按同口径比较；
- 超出允许范围的耗时偏差已解释并接受，或已修复复验；
- 没有影响本次验收的开放阻断项或未验证待测项；
- 用户查看录屏后认可。

没有视频或参考时间不足时，明确写“耗时未验证”。
可以交付候选版本，不得宣称整队实测完成。
未达到时，按差异返回对应阶段继续。
