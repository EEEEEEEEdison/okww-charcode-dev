# 信息获取、证据与阶段交接

每次先确定需要判断什么，再获取支持判断的证据。
只检查影响当前任务的项目。

## 1 信息获取范围

| 方面 | 检查内容 | 记录位置 |
|---|---|---|
| 任务目标 | 所选轴、片段、启动与循环范围、验收目标 | `notes.md`、`timeline.json` 的 `case` |
| 素材内容 | 文字轴、记号、口播、字幕、简介、评论、完整演示 | `media/info.md`、`sources` |
| 适用条件 | 作者与用户的共鸣链、关键装备、初始资源、游戏及框架版本 | `sources.conditions`、`baseline.md` |
| 动作语义 | 前置状态、按法、触发条件、完成信号、可中断时机 | `steps`、`decisions` |
| 跨动作依赖 | 资源获得与消耗、后台效果、延迟生效、增益窗口、跨轮继承 | `decisions`、`steps[].depends_on` |
| 时间与变化 | 起止事件、计时口径、冻结、多遍差异、采样精度 | [timing.md](timing.md)、`reference_timings` |
| 场景与干扰 | 敌人状态、距离、位移、受击、提前击杀、输入受阻 | 素材记录、实测 `notes.md` |
| 实现与实测 | 实际代码版本、函数语义、日志判据、对应录屏 | `baseline.md`、实测 `notes.md` |

尚未影响当前行为的条件，可记为未知。
条件会改变分支或验收时，必须补证或列为阻断项。

## 2 来源与获取方式

可使用以下来源：

- 用户提供的文字轴、攻略、游戏内说明和回答；
- 教程视频的完整画面、口播、字幕、简介和评论；
- 游戏内说明、官方更新资料中影响当前判断的条目；
- 语义卡、上游源码、在线工坊代码和用户历史版本；
- 对应版本的实测日志和录屏。

公开素材和工坊接口可只读获取。不得使用登录凭据。
游戏内说明优先复用已有截图。缺少截图时，可请用户提供。
获取官方资料时，记录版本、原文位置和访问日期。
不得以第三方 wiki 替代角色证据。
下载的工坊代码只读，不运行、不导入。

先查看选定片段的完整画面，再裁 HUD 或动作区域。
发现口播或字幕包含操作条件时，获取对应内容。
自动转写、字幕识别和截图识别必须回原素材核对关键句。
无法获取某一渠道时，记录缺失内容及其影响。

粗扫定位事件后，再查看关键分界点的前后帧。
复用已有证据后仍缺什么，再补采对应素材。
判断已有依据且未知已有处理办法时，停止扩采。

## 3 证据如何支持结论

A/B/C/D 只表示画面来源，不表示结论已经成立：

| 标签 | 来源 | 使用边界 |
|---|---|---|
| A | 按键显示 | 能说明输入发生；不能独立证明动作成功 |
| B | HUD（界面状态）变化 | 能说明显示状态变化；必须核对状态含义 |
| C | 角色或敌人动作 | 必须排查相似动作、遮挡和受击 |
| D | 时间推断 | 必须记录锚点、条件和推断依据 |
| none | 没有可用画面 | 必须改用可定位来源，或登记缺项 |

日志中的 `ok` 只说明程序判据成立。
必须核对函数返回时机及判据能证明的行为。
已有代码能提供实现线索，不能独立证明教程意图。
重复出现的顺序不能独立证明因果关系。
不得把未观察到写成未发生。

每个关键判断必须区分：

1. **观测**：画面、原文或日志直接显示了什么。
2. **解释**：观测支持哪种动作或状态判断。
3. **实现选择**：代码采用什么判据和处理方法。

来源必须能定位到视频时刻、原文位置或代码版本及行号。
画面结论保留帧路径和采样精度。
出现冲突时，先检查版本、初始状态和事件定义。
仍不能解释时，保留冲突双方，登记缺项。
不得设置适用于所有判断的来源优先级。
操作意图查作者说明；程序语义查源码；运行结果查实测。

## 4 缺项分级

| 类别 `impact` | 判定 | 处理 |
|---|---|---|
| `blocking` 阻断项 | 会改变顺序、分支、成功判据或退出条件 | 补证后才能确定受影响的实现 |
| `trial` 待测项 | 实现方向明确，数值或适用范围待验证 | 可进入试验版本，记录假设和验证办法 |
| `noncritical` 非关键项 | 不影响当前行为与验收 | 可记录后继续 |

缺项用 `issues` 记录，字段见 [timeline.md](timeline.md)。
没有整队时序的局部任务，可在 `notes.md` 按同样内容记录。

- 阻断项未解决时，不得通过 G2。
- 待测项必须有试验取值、验证办法和失败处理。
- 非关键项必须说明为何不影响当前任务。
- 用户确认意图后，只解决对应的意图问题。
- 机制是否成立、数值是否适用，仍按各自证据验证。
- C/D 推断会改变行为且缺少已确认知识时，列为阻断项。
- 提问必须说明证据、推荐判断和答案会改变的行为。
- 用户回答后，更新缺项状态和受影响的判断。

## 5 阶段交接

关键判断至少保留六项：

**结论、依据、适用条件、未知、影响范围、验证办法。**

能放入动作字段的内容直接写入 `timeline.json`。
跨节点判断写入 `decisions`，字段见 timeline.md。
代码语义和借用来源写入 `baseline.md`。
实现取舍、验证结果及阶段状态写入 `notes.md`。
同一事实只维护一处，其他产物引用该位置。

阶段结束时，在 `notes.md` 更新：

| 项目 | 内容 |
|---|---|
| 当前阶段 | 阶段名称、通过或阻塞 |
| 输入 | 素材、代码和规则的版本与路径 |
| 输出 | 交付物路径，以及支持下一阶段的结论 |
| 未知 | 缺项编号、影响和处理方式 |
| 检查结果 | 实际执行的检查、结果及证据位置 |
| 下一步 | 下一阶段，或退回哪个阶段补什么 |

下一阶段必须检查输入条件。
发现前提错误时，退回负责该前提的阶段。
局部修改只更新受影响的判断和验证记录。
