# 实测迭代

实测同时检查动作效果、触发、切人和耗时。
只提供日志时，可以定位程序行为，不能完成视频时间验收。
证据规则见 [evidence.md](evidence.md)，时间比较见 [timing.md](timing.md)。

## 1 输入与版本核对

没有实测产物时，读取 [MCP Skill](../skills/mcp/SKILL.md) 准备并执行测试。
已配置 ok-ww MCP 时，进场、开战、录像和报告都自动完成，见 [mcp-testing.md](../references/mcp-testing.md)。
直接测试只需待测代码和成败判据，不必先建立文字轴或整队时序。
已有证据能回答目标时，不必重跑。
以下输入按本轮测试范围核对；模型与参考视频仅在对照时需要。

- 实际运行的代码版本、zip 路径或校验值；
- ok-ww 框架版本、角色共鸣链、初始资源及场景；
- 对应运行的 `logs/ok-script.log`，通常只有 info 及以上；
- 实测录屏、该版 timeline、参考视频及待测项。

缺少录屏时，先分析日志并标出验证限制。
日志与录屏必须能确认属于同次运行。
版本不明且会影响结论时，先补证，不得混用结果。

### 1.1 三种用法

| 用法 | 输入 | 做法 | 通过条件 |
|---|---|---|---|
| 从头制作 | 文字轴、参考视频 | 按阶段生成代码并迭代；MCP 报告作为参考，与视频对照 | §6 |
| 只测稳定性 | 用户提交的 zip | 只运行 MCP 实测，不改代码 | 不判通过，每局写任务状态、是否打到结算、问题行条数与类别 |
| 按 MCP 结果迭代 | 用户提交的 zip，没有参考视频 | 按 MCP 报告的问题行改代码，上限见 §4.1 | 候选版连续 2 局没有问题行 |

用户提交 zip 但没说要改代码时，按“只测稳定性”执行。
问题行指 `report.md` 列出的 `fail`、`fallback`、`interrupt`、warning 及以上级别、脱战和找不到下一个角色。
后两种用法没有耗时基准，不设验收目标，不做时间比较。结论必须写“耗时未验证”，不得写成整队验收完成。

按 MCP 结果迭代时，先把提交的 zip 解包为起点版本 `<队名>/skilltest-v<N>/`。
`<队名>` 取 team.json 的 `name`；N 取该目录下已有的最大编号加 1，没有时为 1。
起点版本的 `notes.md` 记录 zip 路径和 sha256；改动写入下一版。

## 2 日志与模型核对

按节点检查 `enter` → `exit`，核对是否跳节点或交还框架。
统计 `cast X: ok|fail`、`fallback` 和 `interrupt`。
MCP 实测的 `report/report.md` 已列出这些统计，问题行附录像秒数和帧拼图。
对照模型检查技能触发、完成和依赖是否达成。
按 `switch_next_char` 的 `has_intro`、`current_con` 核对切人。
日志缺失或字段含义不明时，回到源码核对判据。
画面卡住时，卡点前最后一行 `wait` 指出卡在哪个等待。probe 行按 logging.md L-11 处理。

`enter`、发送按键和确认换人可能是不同事件。
日志 `ok` 不能独立证明目标动作完整结束。
根因方法见 [rules.md](../rules.md) 5-8。

## 3 视频与耗时比较

按 [step1.md §4](step1.md) 查看完整画面和关键区域。
按 timing.md 使用相同事件与口径测量。
不得统一把双方第一次切人当作任何区间的零点。
启动轴和循环轴分别选择同一语义起点。
有剪辑、加速或冻结差异时，先记录可比范围。

输出：

1. 简单验收表：技能 / 目标次数 / 实测次数 / 是否达标。
2. 未达标类型表：类型 / 第一处偏离 / 缺的次数 / 累计差值。简单验收未达标时必须输出，判定见 §3.2。
3. 时间差异表：按 timing.md §4，含本段和累计差值。
4. 动作差异表：节点 / 预期 / 实际 / 证据 / 影响。
5. 切人核对表：出场节点 / 预期类型 / 实际类型 / 协奏证据 / 下个节点。
6. 待测项结果：缺项编号 / 验证结果 / 新证据 / 后续处理。

每轮实测后，必须按 [evidence.md §4](evidence.md) 回写缺项记录。
有整队时序时，更新当前版本的 `timeline.json.issues`。
局部任务没有整队时序时，更新 `notes.md` 中的唯一记录。
差异表与阶段记录只引用缺项编号及证据，不再维护另一份状态。

先比较整轮，再定位角色节点和关键动作段。
出现超出参考范围的偏差时，检查边界和干扰后分析内部事件。
不能解释的偏差保留为缺项，不得以无 fallback 判为通过。

### 3.1 验收判定

从头制作时，每轮按 `timeline.json.acceptance` 判定。
`acceptance` 缺失时，必须先按 [step1.md §7.1](step1.md#71-验收目标) 补写。

- 实测次数按 `log_match` 统计 `report/run.log`，并在录像里核对。
- 判定顺序：简单验收达标后，才判详细验收。
- 简单验收未达标时，必须先按 §3.2 判未达标类型，再排改动顺序。
- 简单验收未达标时，也必须输出时间差异表。原因：次数只说明没走完，差在哪要看节点耗时。
- 节点链没有偏离时，改动必须按累计差值的贡献从大到小排序。问题行和分数不作排序依据。
- 详细验收必须同时核对 `state_checks`。原因：耗时一致不代表状态一致。

例：今长卜第 11 局第 3 遍 `Jinhsi.S5` 耗时 3.78 s，教程 3.76 s，下一次入场协奏仍比教程少。

### 3.2 未达标类型

简单验收未达标时，按以下顺序判定：

1. 沿节点链找第一处偏离。偏离指以下任一项：`fallback`、`cast X: fail`、`has_intro` 与模型不符、节点跳转与模型不符、录像里的动作与模型不符。计时器归零后出现的项不算偏离。
2. 有偏离时，判为走错，先查第一处偏离。之后的偏差先按连锁处理，不单独改。原因：连锁偏差的耗时和状态会随第一处偏离变化。
3. 没有偏离且计时器归零才停时，判为时间不够，改动顺序按 §3.1。
4. 两类都有时，必须分开记录缺的次数和累计差值。

复验时，必须先看第一处偏离是否消失或后移，再看次数和耗时。
第一处偏离没有消失也没有后移时，判改法无效，不得转去压耗时。

例：今长卜第 18 局按累计差值排序会先改 `Jinhsi.S5`（+1.38 s）。第一处偏离是 `Douling.S1` 第 2 遍切人没有变奏，`Jinhsi.S1` 第 2 遍的 `fallback` 紧随其后。
例：今长卜第 19 局 E4 少 2 个、R 少 1 个。`Jinhsi.S8` 走错丢 1 个 E4；计时器归零时，1 个 R 和 1 个 E4 没走到。

### 已验证的取证技巧

以下是具体案例的方法与观察值，不能直接作为所有角色的常量。

- **日志对应视频**：弗坎嘉 v10、v11 用 R 后 HUD 恢复首帧对应 `cast R: ok`，两次误差 ≤0.005 秒。E 冷却首帧比 `cast E: ok` 早 0.16–0.34 秒，只能粗定位。必须先核对当前函数返回语义，并用第二个事件复核偏移。时间换算用脚本，不心算。
- **游戏时间**：同一计时器的差值表示游戏耗时。用技能 CD 替代时，先确认冷却首帧读数及中途是否刷新。弗洛洛案例的首帧为 11.4，不能直接用于其他技能。
- **换人时刻**：生命上限数字能辅助确认角色。弗坎嘉 25 秒轴嘉 s3→坎 s3，按 HUD 样式误定为 107.70 秒，生命上限在 107.10 秒已变化，用户于 2026-10-15 确认。数字相同或遮挡时，必须另用角色与图标复核。
- **冻结排查**：真实与游戏耗时的差值超出采样误差时，细看计时器停走。弗坎嘉案例中的击破停走为 1.3–1.5 秒，之后出现大额白字，见 basics.md H-5。不得单凭停走时长认定击破。
- **整体表现**：同一挑战、同样条件下的结算分数可辅助比较。弗坎嘉 v10 为 5978 分，v11 首版为 5419 分。分数不能替代动作与耗时检查。

## 4 根因、修改与复验

先区分观测、解释和待验证假设，再说明根因与改法。
已有明确修复授权时，执行授权范围内的改动。
关键意图仍不明确时，使用结构化提问工具确认。
根因不明时，不加兜底。
每个试验围绕一个可验证假设，隔离因果影响。
同一版代码的问题只在 1 局出现时，先用同一版再测 1 局。
复现后才改代码；没有复现时，在 `notes.md` 记为待观察，不改代码。

按根因选择阶段：

| 根因 | 返回阶段 |
|---|---|
| 作者意图、按法、依赖或切人解释错误 | [轴解析](../skills/rotation/SKILL.md) |
| 事件边界、口径、参考测量或模型错误 | [时序建模](../skills/timeline/SKILL.md) |
| 函数语义、判据或等待实现错误 | [代码实现](../skills/implementation/SKILL.md) |
| 来源缺失、片段不可读 | [素材获取](../skills/materials/SKILL.md) |

修改写入 `skilltest-v<N+1>`，不得覆盖旧版。
沿用的 timeline、baseline 和待测项也必须能从新版定位。
改变动作理解或时序时，更新模型并重查受影响的 G2 项。
然后执行 [step2.md §6–8](step2.md) 的定向检查与打包。

### 4.1 自主迭代上限

用户授权自主迭代后，Agent 可连续执行“实测 → 分析 → 改代码 → 打包 → 导入 → 实测”，每次改动前不再询问。
授权没写上限时，每个会话的上限是：

- 新版本不超过 3 个；
- MCP 实测不超过 6 局，按 `matrix_run.py` 的运行次数计。

出现以下任一情况时，必须停止并向用户报告：

- 达到上限；
- 根因不明，下一步只能靠猜；
- 修复需要改变已确认的动作意图；
- 同一步骤连续失败 2 次。

报告必须写第一处偏离的节点、录像秒数、日志现象和要用户对照的问题。

候选版连续 2 局满足通过条件后，停止迭代，请用户查看这 2 局的录像。
从头制作时，通过条件是 §6 除用户认可以外的各项；按 MCP 结果迭代时，按 §1.1。

新版本 `notes.md` 必须记录：

- 输入版本、录屏、日志和运行条件；
- 差异表、证据路径及计时口径；
- 根因、替代解释和仍未验证的假设；
- 修改位置、预期效果和复验办法；
- 简单验收未达标时的未达标类型、第一处偏离和复验结果；
- 参考测量修正及依据，或沿用的参考记录；
- 待测项记录位置及编号、检查结果和下一阶段。

截图和分析文件放在媒体目录，notes 写相对路径。
README 的出处引用原视频、文字轴和 timeline。

## 5 案例证据

把用户反馈、实测判据和已验证的代码改法记录在本案。
来源必须定位到版本、函数、日志或录屏时刻。
尚未实测的改法标明验证状态。
知识使用边界见 [语义卡说明](../knowledge/cards/README.md#使用边界)。

每轮更新 `timeline.json.issues` 后，必须在本案的知识候选清单 `<工作区>/<队名>/knowledge-candidates.md` 登记：

- 登记范围：本轮新增的 issue，以及 `status` 或 `answer` 改过的 issue；与现有卡冲突的已验证证据也要登记。
- 登记不看是否满足入卡条件。是否入卡只写在处理状态里。
- 每个登记范围内的 issue id 必须出现在清单某一行的出处里。同一 issue 已有行时更新该行，不新增。
- 清单跨版本累计，不得随版本目录新建。
- 每条写编号、适用范围（角色与共鸣链，或“通用”）、结论、出处、验证状态和处理状态。
- 与卡冲突时，结论还必须写明卡文件、行号、卡原文、适用条件和影响。
- 出处必须写 issue id，并定位到版本目录内的文件与行号，或日志、录屏时刻。
- 处理状态取以下之一：
  - “待处理”：满足入卡条件。
  - “待验证：<缺什么>”：可能入卡，证据还不够。后续轮次补足证据时改为“待处理”。
  - “不提议：<原因>”：例如只适用当前轴、改法已撤回、属于帧数据、因果未验证。
  - 提议阶段写入的处理结果。
- 清单开头必须有一行“已登记到：<版本目录>”。每轮登记完，改成本轮的版本目录。
- 入卡条件见 [knowledge-maintenance.md §2](../maintainer/knowledge-maintenance.md)。

## 6 完成标准

局部战斗行为测试按本轮成败判据交付证据和未验证项。
局部通过不能推断整队、性能或视频时序验收完成。
以下标准用于整队实测验收。

默认沿用用户为弗坎嘉确定的连续 2 场标准。
其他队伍可按已有明确约定调整。
同一版代码的两场实测必须同时满足：

- 简单验收全部达到 `acceptance.simple` 的目标次数；
- 日志没有 `fallback`，节点链和动作判据符合模型；
- 触发方式、协奏切人和依赖符合已确认意图；
- 整轮、节点和关键动作段已按同口径比较；
- 累计差值不超过 `acceptance.detailed.budget_s`，或超出的秒数已经用户接受；
- 超出允许范围的耗时偏差已解释并接受，或已修复复验；
- 没有影响本次验收的开放阻断项或未验证待测项；
- 用户查看这两场的录屏后认可。

自主迭代时，中间版本由 Agent 按日志和录像判定，只把满足其余各项的版本交给用户查看。

没有视频或参考时间不足时，明确写“耗时未验证”。
可以交付候选版本，不得宣称整队实测完成。
未达到时，按差异返回对应阶段继续。
